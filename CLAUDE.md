# pg-gui

A PostgreSQL GUI client built with GPUI (Zed's UI framework) and gpui-component. Rust 2024 edition.

## Formatting and linting — required after every change

After ANY change to Rust code or `Cargo.toml`, run both of these and fix every finding before considering the change done:

```sh
cargo fmt
cargo clippy --all-targets -- -W clippy::pedantic -D warnings
```

- Clippy pedantic is the project lint level. Do not silence findings with broad `#[allow(...)]`; fix the code. A targeted `#[allow]` with a short justification comment is acceptable only when a pedantic lint is a genuine false positive.
- Never commit code that fails either command.

## Build & run

```sh
cargo run              # dev build (deps are built with opt-level 3; keep it that way, gpui is unusable otherwise)
docker compose up -d   # local PostgreSQL (host port 5433, user/pass/db: pgui/pgui/pgui_test)
```

Never run Docker or database actions yourself — no starting the daemon, no `docker compose up/down`, no `docker exec`, no psql/DDL/DML against the database. The user does all of that manually. If a task needs the database in some state, tell the user what is needed and wait.

PL/pgSQL step debugging (`src/debug.rs`) drives EnterpriseDB's pldebugger (the `pldbg_*` proxy API) through the [`pgdap`](https://github.com/gintsgints/pgdap) crate, embedded as a **library** (`pgdap::debugger::DebugSession`) rather than spawned as a DAP server binary — same approach as the LSP below. pldebugger needs **two** connections that both block: a persistent *controller* (arms breakpoints, steps, reads stack/vars) and a *target* that runs the debugged routine and stays trapped in the backend until continued. `debug::Session::start` spawns a controller thread which, after arming the entry global breakpoint, spawns the target thread (so the trap is set before the routine runs); commands go in over a `std::sync::mpsc` channel, `DebugEvent`s come out over a `futures` `UnboundedReceiver` the UI awaits like LSP diagnostics — never the UI thread. The target statement is built here (not by pgdap, whose binary only emits `SELECT`): procedures use `CALL`, set-returning functions `SELECT * FROM f(..)`, else scalar `SELECT`, via a `prokind`/`proretset` lookup. Breakpoint line numbers are body-relative to `pldbg_get_source` (no disk source mapping yet). Two setups can never trap and every `pldbg_*` call still succeeds under them, so `debug::preflight` rejects them before arming anything: a routine that is not `LANGUAGE plpgsql`, and a server without `plugin_debugger` in `shared_preload_libraries`. Anything else that runs straight through is caught at the other end — the control connection carries a per-session `application_name`, and a target that finishes while `attached` is still false explains the miss and cancels the controller's `pldbg_wait_for_target` (which would otherwise park forever). Requires the `pldbgapi` extension (`sql/extensions/R.0.01.02.1__pldbgapi.sql`) and `plugin_debugger` in `shared_preload_libraries`. UI: the debug panel (`render_debug_panel`) replaces the results table while a session is active — variables (click to `deposit_value`) over the call stack (click to `select_frame`), a Step Over/Into/Continue/Stop toolbar, and, before the first stop, the progress/output pane (`render_debug_status`) so a run that never traps is visible; also the Debug menu and F5/F10/F11/Shift-F5. The stepped source is read in the editor, not the panel: each stop selects the executing line in the tab the session was launched from (`DebugState::tab_id`), scrolling it into view (`debug::editor_line_of`, which locates `pldbg_get_source` verbatim in the buffer — body line 1 is the `$tag$` line — and no-ops when the buffer does not hold that body, so a routine stepped into from elsewhere never highlights an unrelated line). The editor's own breakpoint gutter is the only breakpoint UI; toggling one mid-run arms/drops it on the live session (`sync_debug_breakpoint`), which sends the raw 0-based editor row — the controller owns the row→body-line mapping (`body_line_of`) because breakpoints always go on the *entry* routine (`Entry { oid, editor_text, body }`, captured at attach), not on whatever frame the panel is inspecting.

`StopState` describes the *selected* frame, not always the innermost one: `report_frame(level)` reads the source/line of that frame and `pldbg_get_variables` (which reports whichever frame `pldbg_select_frame` last selected), and `command_loop` tracks the level — set by `SelectFrame`, reset to 0 by every step/continue, reused by `Deposit` so an edited value re-reads in the frame it was edited in. `StopState::frame` carries it to the UI, which marks that row in the call stack and selects that frame's line in the editor. `docs/debug/EXAMPLE.md` documents the raw `pldbg_*` flow the sample `place_order` procedure is debugged with. Note: pgdap needs a `[lib]` target (`src/lib.rs` exposing `pub mod debugger;`) for this dependency — until that lands upstream, `Cargo.toml` points at a local path checkout.

A tab holding exactly one `CREATE FUNCTION`/`PROCEDURE` numbers its gutter the way Postgres numbers that routine in error messages and `pldbg` frames: body-relative, where body line 1 is the line carrying the opening `$tag$`, so the lines above it read 0, -1, -2. `statement::body_line_offset` finds that delimiter (skipping strings, comments, and `$1` placeholders, and bailing out to plain file numbering when the buffer holds no routine or several) and the result is fed to gpui-component's `InputState::line_number_offset` — a fork addition (branch `line_number_offset`, merged into `my_fixes2`) that shifts the drawn numbers only. Everything else — breakpoints, cursor, diagnostics — still speaks 0-based buffer rows.

SQL editor language support (completions, hover, diagnostics, formatting) comes from the Postgres Language Server, embedded as a **library** rather than spawned as a binary. `src/lsp.rs` depends on the `pgls_*` crates (git dependency on the fork <https://github.com/gintsgints/postgres-language-server>, branch `preserve_comments`) and drives its `Workspace` trait directly: `server_sync()` → `register_project_folder` + `update_settings` (db credentials derived from the connection string, plus formatter casing) → `open_file`. Completions and hover call the workspace synchronously on a background executor; every write to the workspace document (`change_file`, formatting, `close_file`) goes through a dedicated document-worker thread fed by a channel — never the UI thread, because diagnostics hold the workspace's document lock across database connection attempts (seconds when the server is unreachable). The worker also pulls diagnostics on a debounce after each change and pushes them to the editor through a channel. Completion results are prefixed with snippet suggestions (`snippets::suggestions`, matched against the words before the cursor), and a snippets-only provider (`lsp::SnippetCompletions`) is installed while the server is offline. There is no external process, config file, or `postgrestools` binary anymore, and no `~/Library/Caches/pg-gui/lsp-workspace/` config to write. Because `pgls_query` builds `libpg_query` from source (via `bindgen`/`cc`), the first build is slow and needs a working C toolchain + libclang. Format-on-save (`format_on_save` in config.json, **on** by default), toggled at runtime from the clickable `fmt: on`/`fmt: off` segment in the status bar or the check-marked Edit ▸ Format on Save menu item (both dispatch `ToggleFormatOnSave`, which persists the flag and rebuilds the menus for the check-mark); `keyword_case` and `constant_case` (`"lower"`/`"upper"`, default lower) set the formatter's casing. An `#[ignore]`d integration test (`lsp::tests::embedded_server_*`) exercises completions/diagnostics/formatting against the docker DB — run with `cargo test -- --ignored embedded_server`.
